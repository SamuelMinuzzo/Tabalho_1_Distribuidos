\begin{abstract}
Este trabalho apresenta a implementação e a análise de versões sequenciais e paralelas para o problema de busca de substrings em arquivos de texto grandes. As respectivas versões foram desenvolvidas nas linguagens de programação C e Java. Em C, a paralelização foi realizada utilizando o padrão OpenMP,por meio de diretivas \texttt{\#pragma omp}, enquanto em Java foi utilizada uma abordagem com múltiplas threads por meio do Framework \textit{ExecutorService}. O núcleo algorítmico das soluções é baseado no algoritmo Boyer-Moore-Horspool (BMH), adaptado para processamento de dados em blocos. Os resultados experimentais são comparados em termos de tempo de execução e \textit{speedup}, com o objetivo de avaliar a eficiência das abordagens adotadas em diferentes tamanhos de entrada, variando de 0,1 GB a 16 GB, e diferentes quantidades de threads, de 1 a 200.
\end{abstract}

\textbf{Palavras-chave:} Programação Paralela, Boyer-Moore-Horspool, OpenMP, Threads, Busca de Substrings, Desempenho.

\section{Introdução}

A busca por padrões em texto é um problema clássico da computação, presente em aplicações como indexação de documentos, sistemas de busca, mineração de dados, bioinformática, análise forense, processamento de logs e monitoramento de sistemas. À medida que o volume de dados cresce, abordagens simples de comparação caractere a caractere tornam-se progressivamente mais custosas, tornando necessário o uso de algoritmos mais eficientes e a utilização de técnicas de paralelização.

Neste trabalho, foi estudado o problema de contagem de ocorrências de substrings em arquivos texto com tamanhos variáveis, desde algumas centenas de megabytes até múltiplos gigabytes. O foco da análise foi avaliar como as diferentes escolhas de implementação impactam o desempenho computacional.

A motivação do trabalho está diretamente associada à necessidade de compreender, na prática, como conceitos de programação paralela podem ser aplicados a um problema real de processamento intensivo de dados. Além disso, o tema permite comparar dois aspectos importantes da computação de alto desempenho: a eficiência algorítmica e a eficiência da exploração de paralelismo.

O objetivo geral do trabalho é implementar, executar e comparar quatro versões do problema:

\begin{itemize}[leftmargin=*]
    \item versão sequencial em Java;
    \item versão paralela em Java utilizando threads;
    \item versão sequencial em C;
    \item versão paralela em C utilizando OpenMP.
\end{itemize}

\section{Descrição do Problema}

O problema tratado neste trabalho consiste em contar o número de ocorrências de uma determinada substring em um arquivo texto de grande porte. Diferentemente de uma busca por ``palavra inteira'', a proposta adotada considera ocorrências de substring no sentido literal, isto é, toda sequência de bytes compatível com o padrão buscado deve ser contabilizada, inclusive ocorrências sobrepostas.

\subsection{Definição formal}

Dado:

\begin{itemize}[leftmargin=*]
    \item um arquivo texto $T$ com comprimento $n$ bytes;
    \item uma substring padrão $P$ com comprimento $m$ bytes, com $1 \leq m \leq n$;
\end{itemize}

deve-se determinar o número de índices $i$ tais que:

\[
T[i..i+m-1] = P
\]

onde $0 \leq i \leq n-m$.

No contexto deste trabalho, a entrada é tratada como uma sequência de bytes. Essa decisão simplifica a implementação e torna a solução compatível com diferentes tamanhos de arquivo, embora implique que a interpretação semântica de caracteres multibyte em UTF-8 não seja o foco principal da contagem.

\subsection{Entrada}

A entrada do problema é composta por:

\begin{itemize}[leftmargin=*]
    \item o caminho para um arquivo texto;
    \item a substring que será procurada;
    \item o número de threads desejadas (utilizada para as versões paralelas).
\end{itemize}

\subsection{Saída}

A saída consiste em:

\begin{itemize}[leftmargin=*]
    \item o número total de ocorrências encontradas;
    \item o tempo de execução da versão sequencial;
    \item o tempo de execução da versão paralela;
    \item o \textit{speedup} calculado a partir desses tempos.
\end{itemize}

\subsection{Complexidade esperada}

Uma solução ingênua para o problema, baseada em comparação direta do padrão em todas as posições possíveis, possui complexidade de pior caso aproximadamente $O(n \cdot m)$. Para arquivos muito grandes, esse custo pode tornar-se significativo.

Neste trabalho, a principal estratégia algorítmica adotada nas implementações foi o algoritmo Boyer-Moore-Horspool, que, embora também possa apresentar pior caso $O(n \cdot m)$ em situações onde a substring apresenta tamanho unitário, ou ainda, substrings sobrepostas, tende a apresentar desempenho ligeiramente superior na prática, quando se considera textos reais, pois utiliza deslocamentos que permitem pular posições do texto sem comparação completa em todas elas.

Além da eficiência algorítmica, o problema também se mostrou adequado para paralelização, desde que o espaço de busca seja dividido cuidadosamente e que as fronteiras entre blocos sejam tratadas de forma correta para evitar perda ou dupla contagem de ocorrências.

\section{Fundamentação Teórica}

\subsection{Busca de padrões em texto}

A busca de padrões em texto pode ser realizada por diferentes estratégias. A abordagem mais simples consiste em alinhar o padrão em cada posição do texto e comparar os caracteres sequencialmente. Essa solução é conceitualmente simples, porém pouco eficiente para arquivos muito grandes, especialmente quando o padrão possui mais de um caractere.

Algoritmos mais avançados exploram pré-processamento do padrão para reduzir o número de comparações efetivas. Entre os algoritmos clássicos, destacam-se Boyer-Moore, Knuth-Morris-Pratt e Boyer-Moore-Horspool. Neste trabalho, o algoritmo central das implementações autorais foi o Boyer-Moore-Horspool, por apresentar boa relação entre simplicidade de implementação e desempenho prático.

\subsection{O algoritmo Boyer-Moore-Horspool (BMH)}

O algoritmo Boyer-Moore-Horspool é uma variação simplificada do algoritmo de Boyer-Moore. Sua principal ideia é comparar o padrão com o texto a partir do último caractere do padrão. Quando ocorre uma discrepância, em vez de avançar apenas uma posição, o algoritmo usa uma tabela de deslocamentos para determinar quantas posições o padrão pode ser movido com segurança.

\subsubsection{Pré-processamento}

Seja $P$ o padrão de comprimento $m$. Constrói-se uma tabela de deslocamento para todos os possíveis valores de byte. Inicialmente, todos os deslocamentos recebem o valor $m$. Em seguida, para cada posição do padrão, exceto a última, define-se:

\[
shift[P[i]] = m - 1 - i
\]

para $0 \leq i < m-1$.

Essa tabela informa o quanto o padrão pode ser deslocado quando o caractere alinhado ao final da janela de comparação causa um erro de correspondência.
A implementação da contrução da tabela de saltos em C ilustra a simplicidade e eficiência do pré-processamento do algoritmo,


\subsubsection{Funcionamento}

Em cada etapa:

\begin{enumerate}[leftmargin=*]
    \item alinha-se o padrão a uma posição do texto;
    \item compara-se o último caractere do padrão com o caractere correspondente do texto;
    \item se houver coincidência, prossegue-se a comparação de trás para frente;
    \item se houver erro, consulta-se a tabela de deslocamento e o padrão é movido adequadamente.
\end{enumerate}

\subsubsection{Exemplo conceitual}

Suponha o padrão \texttt{como}, o  último caractere é \texttt{o}. Ao alinhar o padrão a uma posição do texto, o algoritmo observa primeiramente o byte correspondente a \texttt{o}. Se esse byte não coincidir, não é necessário comparar os demais bytes; o deslocamento é determinado diretamente pela tabela.

Esse comportamento reduz significativamente o número de comparações, principalmente quando o alfabeto do texto é relativamente amplo e o padrão não aparece com extrema frequência.

\subsubsection{Vantagens do BMH}

As principais vantagens do BMH são:

\begin{itemize}[leftmargin=*]
    \item implementação relativamente simples;
    \item bom desempenho prático em busca de substrings;
    \item redução do número de comparações em relação à busca direta;
    \item excelente adaptação para tratamento byte a byte;
    \item boa integração com leitura em blocos para arquivos grandes.
\end{itemize}

\begin{lstlisting}[language=C, caption={Construção da tabela de deslocamentos do BMH em C}]
static inline void monta_tabela_deslocamento(
    const unsigned char *palavra,
    size_t tamanho_palavra,
    size_t *tabela
) {
    for (size_t i = 0; i < 256; ++i) {
        tabela[i] = tamanho_palavra;
    }

    if (tamanho_palavra >= 2) {
        for (size_t i = 0; i < tamanho_palavra - 1; ++i) {
            tabela[palavra[i]] = tamanho_palavra - 1 - i;
        }
    }
}
\end{lstlisting}

\subsubsection{Desvantagens do BMH}

Como limitações, destacam-se:

\begin{itemize}[leftmargin=*]
    \item pior caso ainda proporcional a $O(n \cdot m)$, atingido quando o padrão é altamente periódico e o texto é composto por repetições do mesmo caractere, o que minimiza os deslocamentos da tabela;
    \item necessidade de cuidado extra ao dividir o texto para processamento paralelo, especialmente no tratamento de ocorrências nas fronteiras entre partições;
    \item menor aproveitamento dos saltos quando o padrão é muito curto, especialmente de tamanho 1 (pior cenário), pois a tabela de deslocamento retorna sempre 1 independentemente do caractere encontrado, reduzindo o algoritmo a uma varredura completa.
\end{itemize}


\subsection{Paralelização do problema}

A paralelização da busca de substrings não é trivial, pois o texto não pode ser simplesmente dividido em partes independentes sem considerar as fronteiras. Se uma ocorrência começar no final de um bloco e terminar no início do próximo, ela poderá ser perdida.

Para resolver esse problema, as implementações paralelas adotaram estratégias de sobreposição ou de propriedade de intervalo:

\begin{itemize}[leftmargin=*]
    \item \textbf{sobreposição entre blocos:} cada bloco é lido com alguns bytes adicionais do bloco seguinte;
    \item \textbf{intervalo de propriedade:} cada thread pode inspecionar além do seu limite, mas só contabiliza ocorrências cujo índice inicial pertence ao seu intervalo.
\end{itemize}

Esse cuidado é essencial para garantir correção na contagem.

\section{Implementações}
\subsection{Visão geral das implementações}

As implementações foram organizadas em duas linguagens, C e Java, e em dois modos de execução, sequencial e paralelo. Em ambos os casos, o problema atacado foi o mesmo: contagem de ocorrências de substring em arquivos de grande porte.

\subsection{Versão Sequencial em Java}

A versão sequencial em Java desenvolvida foi construída com foco em manter a mesma lógica algorítmica da versão em C, permitindo uma comparação justa entre linguagens.

\subsubsection{Estrutura da solução}

A implementação realiza:

\begin{enumerate}[leftmargin=*]
    \item leitura do arquivo em blocos com \texttt{BufferedInputStream};
    \item conversão da substring em vetor de bytes;
    \item construção da tabela de deslocamentos do BMH;
    \item execução da busca em cada bloco;
    \item preservação dos últimos $m-1$ bytes entre blocos.
\end{enumerate}

Essa abordagem evita a necessidade de carregar o arquivo inteiro em memória, o que é importante para entradas de múltiplos gigabytes.

\subsubsection{Motivação da escolha}

A escolha pela leitura em blocos na implementação em Java foi motivada principalmente pela necessidade de lidar com arquivos de grande porte sem comprometer o uso de memória. Essa abordagem permite processar o arquivo de forma incremental, evitando a necessidade de carregá-lo integralmente em memória, o que seria inviável para entradas de vários gigabytes. Além disso, essa estratégia facilita a manutenção de uma semântica consistente com a implementação em C, permitindo uma comparação mais justa entre as linguagens. Outro fator relevante foi a facilidade de adaptação dessa estrutura para a versão paralela, uma vez que o processamento em blocos naturalmente se presta à divisão de trabalho entre múltiplas threads.

\subsubsection{Vantagens}

A abordagem adotada apresenta como principal vantagem a boa organização estrutural do código, tornando o fluxo de leitura e processamento mais claro e previsível. O uso de leitura em blocos reduz significativamente o risco de esgotamento de memória, especialmente em cenários com arquivos muito grandes. Além disso, a similaridade conceitual com a versão em C facilita a análise comparativa entre as implementações. Outro ponto positivo é a integração direta com o sistema de automação dos testes, permitindo a execução consistente dos experimentos em diferentes cenários.

\subsubsection{Desvantagens}

Por outro lado, a implementação em Java apresenta algumas desvantagens inerentes à própria linguagem. O uso da máquina virtual introduz um overhead adicional, especialmente em operações intensivas de baixo nível, como o processamento byte a byte realizado pelo algoritmo. Além disso, o gerenciamento automático de memória pode introduzir custos indiretos, como pausas ocasionais do coletor de lixo. Em comparação com a linguagem C, essas características resultam, em geral, em um desempenho inferior em tarefas altamente dependentes de eficiência computacional.

\subsection{Versão Sequencial em C}

A versão sequencial em C foi desenvolvida com base na mesma lógica utilizada na implementação em Java, porém explorando características de mais baixo nível da linguagem. Essa abordagem permite maior controle sobre a alocação de memória, alinhamento de dados e operações de leitura, resultando em uma execução mais eficiente.

\subsubsection{Estrutura da solução}

Na implementação em C, o arquivo é aberto em modo binário e um buffer de entrada é configurado manualmente para otimizar a leitura. Em seguida, é construída a tabela de deslocamentos do algoritmo Boyer-Moore-Horspool. O arquivo é então processado em blocos, preservando uma pequena região de sobreposição entre leituras consecutivas para evitar perda de ocorrências na fronteira dos chunks. Para padrões de tamanho unitário, a implementação utiliza uma estratégia otimizada de contagem direta, reduzindo o custo computacional nesse caso específico.

\subsubsection{Particularidades}

Uma das principais características da implementação em C é o controle mais refinado sobre aspectos internos da execução, como o tamanho dos buffers, o alinhamento em memória e o custo das abstrações utilizadas. Isso permite um uso mais eficiente dos recursos do hardware, além de possibilitar medições de tempo mais precisas.

Adicionalmente, as implementações incorporam o cálculo do salto seguro pós-match por meio da \textit{KMP failure function}. Após confirmar uma ocorrência, o algoritmo original avançaria apenas uma posição, o que é correto mas desnecessariamente lento para padrões sem sobreposição. A função \texttt{calcula\_salto\_pos\_match} pré-computa, a partir do vetor de falha do KMP, o menor avanço seguro após um match que não descarta nenhuma ocorrência sobreposta. Para padrões sem auto-sobreposição, como \texttt{Bacamarte}, o salto é igual ao
comprimento do padrão, maximizando o desempenho. Para padrões com
sobreposição, como \texttt{aaaaaa}, o salto é calculado precisamente para
não perder matches consecutivos, visto que nessa string a palavra "aa" está presente 5 vezes. Esse cálculo é realizado uma única
vez antes do loop de leitura, sem custo adicional por chunk processado.

\begin{lstlisting}[language=C, caption={Cálculo do salto seguro após um match confirmado}]
static size_t calcula_salto_pos_match(const unsigned char *palavra, size_t m) {
    if (m == 0) return 1;
    if (m == 1) return 1;

    size_t *falha = calloc(m, sizeof(size_t));
    if (!falha) return 1;

    falha[0] = 0;
    size_t k = 0;
    for (size_t i = 1; i < m; i++) {
        while (k > 0 && palavra[k] != palavra[i])
            k = falha[k - 1];
        if (palavra[k] == palavra[i])
            k++;
        falha[i] = k;
    }

    size_t salto = m - falha[m - 1];
    free(falha);
    return salto;
}
\end{lstlisting}

\subsubsection{Vantagens}

Como consequência dessas características, a versão em C apresenta maior eficiência de baixo nível, menor overhead de execução e melhor aproveitamento de cache e memória. Além disso, essa implementação serve como uma base sólida para a aplicação de técnicas de paralelização, como o uso de OpenMP.

\subsubsection{Desvantagens}

Em contrapartida, a implementação em C exige maior cuidado por parte do programador, especialmente no gerenciamento de memória e na garantia da corretude do código. A complexidade de implementação é maior, e a portabilidade pode ser reduzida dependendo das configurações do compilador e do ambiente de execução.


\subsection{Versão Paralela com Threads (Java)}

A versão paralela em Java foi construída a partir da versão sequencial, mantendo a mesma lógica de leitura em blocos e o uso do algoritmo Boyer-Moore-Horspool, porém introduzindo paralelismo na etapa de processamento dos dados.

\subsubsection{Estratégia de paralelização}

A estratégia adotada consiste em dividir o espaço de possíveis posições iniciais do padrão dentro de cada bloco entre múltiplas threads. Cada thread é responsável por um intervalo específico, sendo considerada ``proprietária'' das ocorrências cujo índice inicial pertence a esse intervalo. Para evitar perda de ocorrências nas fronteiras, cada thread pode inspecionar uma pequena região adicional além do seu limite, mas contabiliza apenas as ocorrências que realmente pertencem ao seu intervalo. Essa abordagem elimina tanto a perda quanto a duplicação de resultados.

\begin{lstlisting}[language=Java, caption={Divisão do espaço de busca em intervalos de propriedade em Java}]
int totalIniciosValidos = tamanhoTexto - m + 1;
List<Future<Long>> futures = new ArrayList<>(numThreads);

for (int t = 0; t < numThreads; t++) {
    final int inicioPropriedade =
        (int) (((long) totalIniciosValidos * t) / numThreads);
    final int fimPropriedade =
        (int) (((long) totalIniciosValidos * (t + 1)) / numThreads);

    futures.add(executor.submit(() ->
        bmhIntervaloPropriedade(
            texto,
            tamanhoTexto,
            palavra,
            tabela,
            inicioPropriedade,
            fimPropriedade
        )
    ));
}
\end{lstlisting}

\subsubsection{Execução e sincronização}

A execução paralela é gerenciada por meio de um \textit{ExecutorService}, responsável por distribuir as tarefas entre as threads disponíveis. Cada tarefa retorna uma contagem parcial de ocorrências, e a soma final é realizada após a conclusão de todas as execuções. Essa estratégia reduz a necessidade de sincronização explícita e evita o uso de regiões críticas frequentes, o que contribui para um melhor desempenho.

\subsubsection{Vantagens e desvantagens}

A principal vantagem dessa abordagem é a simplicidade estrutural da paralelização, que se integra naturalmente à lógica sequencial já existente. Além disso, o modelo é flexível, permitindo ajustar facilmente o número de threads. No entanto, o uso de threads em Java envolve overhead adicional, tanto na criação quanto no gerenciamento das tarefas, além de depender do comportamento da máquina virtual e do coletor de lixo, o que pode impactar o desempenho em comparação com soluções em C.

\subsection{Versão Paralela com OpenMP (C)}

A versão paralela em C utiliza OpenMP para explorar paralelismo de forma mais direta e eficiente. Nesse caso, a divisão do trabalho segue o mesmo princípio adotado na versão em Java, mas com menor overhead de execução.

\subsubsection{Uso de \texttt{\#pragma omp}}

A paralelização é realizada por meio de diretivas \texttt{\#pragma omp parallel for} combinadas com a cláusula \texttt{reduction}, que permite acumular de forma segura as contagens parciais geradas por cada thread. Esse modelo simplifica a implementação e reduz a necessidade de controle manual de sincronização.

\subsubsection{Double buffering}
A versão paralela em C implementa a técnica de \textit{double buffering} com o objetivo de sobrepor as etapas de E/S e processamento, reduzindo o tempo total de execução. Em vez de executar leitura e processamento de forma sequencial, são utilizados dois buffers alternados que permitem a construção de um pipeline entre CPU e disco. Enquanto um dos buffers é processado pelas threads responsáveis pela busca da substring, o outro é preenchido por uma thread dedicada à leitura do próximo \textit{chunk} a partir do disco, utilizando uma região com \texttt{\#pragma omp parallel sections}. Dessa forma, as operações de leitura e processamento ocorrem de maneira concorrente. Para garantir a corretude na detecção de padrões que cruzam as fronteiras entre \textit{chunks}, uma região de sobreposição (overlap) é copiada do final do buffer atual para o início do próximo antes do início do processamento paralelo. Isso assegura que nenhuma ocorrência da substring seja perdida devido à segmentação dos dados. Com essa abordagem, o tempo total por \textit{chunk} tende a ser limitado pelo máximo entre o tempo de leitura e o tempo de processamento, em vez da soma de ambos. Essa sobreposição é particularmente eficaz quando o sistema não está completamente limitado pela largura de banda de E/S, permitindo melhor aproveitamento dos recursos computacionais.

\begin{lstlisting}[language=C, caption={Sobreposição entre leitura e processamento com double buffering}]
#pragma omp parallel sections num_threads(2)
{
    #pragma omp section
    {
        lidos_prox = fread(buf[proximo] + sobreposicao, 1,
                           (size_t)chunk_real, arquivo);
    }

    #pragma omp section
    {
        total += bmh_paralelo_buffer(
            buf[atual], tamanho_valido, palavra, m,
            tabela, num_threads, salto_match
        );
    }
}
\end{lstlisting}

\subsubsection{Tipo de paralelismo}

O paralelismo utilizado é do tipo \textit{data parallelism}, no qual diferentes threads executam a mesma operação sobre diferentes partes do conjunto de dados.

\subsubsection{Tratamento das fronteiras}

A mesma ideia de intervalo de propriedade foi aplicada: cada thread recebe um conjunto de posições iniciais válidas e pode inspecionar além da sua região, mas apenas contabiliza as ocorrências que efetivamente se iniciam dentro do seu intervalo.

\begin{lstlisting}[language=C, caption={Paralelização da busca no buffer com OpenMP}]
#pragma omp parallel for reduction(+:total) schedule(static) num_threads(num_threads)
for (int t = 0; t < num_threads; ++t) {
    long long inicio_propriedade = (total_inicios_validos * t) / num_threads;
    long long fim_propriedade    = (total_inicios_validos * (t + 1)) / num_threads;

    total += bmh_intervalo_propriedade(
        texto,
        tamanho,
        palavra,
        tamanho_palavra,
        tabela,
        inicio_propriedade,
        fim_propriedade,
        salto_match
    );
}
\end{lstlisting}

\subsubsection{Vantagens}

\begin{itemize}[leftmargin=*]
    \item baixo overhead em relação a outras abordagens de paralelização;
    \item sintaxe direta e integrada ao C;
    \item excelente controle do número de threads;
    \item desempenho geralmente superior ao Java em tarefas intensivas de CPU.
\end{itemize}

\subsubsection{Desvantagens}

\begin{itemize}[leftmargin=*]

\subsection{Métricas}

O desempenho foi avaliado com base principalmente em duas métricas:

\begin{enumerate}[leftmargin=*]
    \item tempo de execução;
    \item \textit{speedup}.
\end{enumerate}

O \textit{speedup} foi calculado por:

\begin{equation}
Speedup = \frac{T_s}{T_p}
\end{equation}

Onde:
\begin{itemize}[leftmargin=*]
    \item $T_s$ = tempo sequencial;
    \item $T_p$ = tempo paralelo.
\end{itemize}

Além disso, a corretude da implementação foi verificada comparando-se, sempre que possível, o número de ocorrências retornado pela versão sequencial com o número obtido pela versão paralela.

\section{Discussão}

A análise dos resultados obtidos evidencia diferenças claras entre as implementações em C e Java, bem como o impacto da paralelização no desempenho do problema.

Inicialmente, observa-se que a implementação em C apresentou desempenho superior em todos os cenários testados. Para arquivos menores, como 0,1 GB, a diferença já é perceptível, com o C executando aproximadamente duas vezes mais rápido que o Java. Essa diferença se mantém consistente conforme o tamanho do arquivo aumenta, sendo atribuída principalmente ao menor overhead da linguagem C e ao controle mais direto sobre memória e operações de baixo nível.

Em relação à paralelização, ambas as linguagens apresentaram ganhos significativos para arquivos de tamanho intermediário. O speedup observado variou entre aproximadamente 1,8x e 2,1x na maioria dos casos, indicando bom aproveitamento do paralelismo disponível. A implementação em C com OpenMP apresentou resultados ligeiramente superiores, especialmente para arquivos entre 2 GB e 10 GB, onde atingiu speedups acima de 2,1x.

Entretanto, para o maior arquivo testado (16GB), houve uma queda significativa no ganho de paralelismo em ambas as linguagens, com speedup próximo de 1,1x. Esse comportamento é explicado pela combinação de dois fatores. Primeiro, um arquivo de 15 GB excede a memória RAM disponível para cache do sistema operacional, forçando leituras diretas do armazenamento a cada chunk. Segundo, a largura de banda do SSD NVMe, embora elevada, torna-se o gargalo dominante quando múltiplas threads demandam dados simultaneamente sem que o sistema consiga antecipar as leituras. Nesse cenário, adicionar mais threads não reduz o tempo de leitura dos dados, e o ganho de CPU fica mascarado pela espera por dados. O tempo sequencial de 41s para 16 GB contra 6,9s para 10 GB — uma razão de 6x para um aumento de 1,5x no tamanho — reforça essa hipótese.

Outro ponto relevante é que o crescimento do tempo de execução não é perfeitamente linear com o tamanho do arquivo, especialmente nas versões paralelas. Isso ocorre devido a fatores como cache, comportamento do sistema operacional e gerenciamento de threads.

De forma geral, os resultados mostram que:

\begin{itemize}
    \item a linguagem C apresentou melhor desempenho em todos os cenários;
    \item o OpenMP proporcionou paralelização mais eficiente que threads em Java;
    \item o ganho de paralelismo é limitado por hardware em grandes volumes de dados;
    \item o algoritmo BMH mostrou-se eficiente e adequado para o problema.
\end{itemize}

\textbf{C vs. Java nos cenários avaliados:}
A implementação em C apresentou desempenho superior em todos os cenários experimentais, tendo maior vantagem em arquivos de tamanho menores a 10GB. Nesses cenário, o C paralelo chegou a atingir aproximadamente o dobro da taxa de processamento do Java paralelo, beneficiando-se de menor overhead de runtime, melhor controle de memória e otimizações de baixo nível. Para o maior volume de dados, a diferença relativa entre as linguagens diminuiu significativamente, pois ambas passaram a ser limitadas pelo mesmo gargalo de entrada/saída, reduzindo o impacto das otimizações computacionais.

\textbf{Cenários em que o paralelismo foi mais vantajoso:}
O paralelismo trouxe maiores ganhos em arquivos de tamanho pequeno a médio, especialmente até cerca de 10 GB, onde o custo de leitura ainda não saturava completamente a largura de banda do sistema de armazenamento. Nesses casos, a divisão do trabalho entre múltiplas threads permitiu explorar melhor os recursos de CPU, reduzindo o tempo total de execução. 

\textbf{Limite de escalabilidade com aumento de threads:}
Os resultados indicam que o ganho de desempenho cresce de forma parcialmente linear com o aumento do número de threads, apresentando boa escalabilidade até aproximadamente 8 threads. A partir desse ponto, os ganhos tornam-se marginais, especialmente entre 8 e 20 threads. Esse comportamento evidencia a transição do gargalo de CPU na leitura do dados, onde a largura de banda de leitura do disco passa a limitar o desempenho global, tornando o aumento adicional de paralelismo pouco efetivo.

\textbf{Influência do tamanho da palavra no desempenho:}
O tamanho da substring teve impacto direto na eficiência do algoritmo. Padrões curtos resultaram em maior número de comparações, pois oferecem menos oportunidades de salto durante a busca. Por outro lado, padrões mais longos permitiram saltos maiores, reduzindo significativamente o número de acessos ao texto e melhorando o throughput. Assim, quanto maior o padrão, menor o custo relativo por byte processado, refletindo em melhores tempos de execução.

\textbf{Comportamento do BMH para padrões curtos e longos:}
Para padrões muito curtos, como uma substring de comprimento unitário, o algoritmo BMH perde sua principal vantagem, já que a tabela de deslocamento tende a retornar valores mínimos (tipicamente 1), resultando em uma varredura praticamente sequencial do texto. Nesse cenário, o desempenho depende fortemente de otimizações adicionais, neste caso o processamento em blocos. Em contraste, para padrões mais longos, o BMH explora eficientemente sua heurística de deslocamento, realizando saltos maiores e reduzindo o número de comparações, levando a um desempenho significativamente superior aos métodos tradicionais.

\section{Dificuldades Encontradas}

Durante o desenvolvimento das implementações, diversas dificuldades técnicas e conceituais foram observadas.

Uma das principais dificuldades foi garantir a corretude da contagem nas regiões de fronteira entre blocos e entre partições paralelas. Como a busca é por substring e não por palavra inteira, uma ocorrência pode iniciar em um bloco e terminar em outro, o que exige tratamento explícito de sobreposição.

Outra dificuldade técnica foi determinar o avanço correto após uma ocorrência confirmada. Um avanço de uma posição é sempre correto, mas desperdiça saltos quando o padrão não tem auto-sobreposição. Um avanço igual ao comprimento do padrão é ótimo para padrões sem sobreposição,
mas perde matches para padrões como \texttt{aa} em \texttt{aaaa}. A solução adotada foi calcular o salto mínimo seguro por meio da \textit{KMP failure function}, que determina o comprimento do maior prefixo do padrão que também é sufixo. Esse cálculo é feito uma única
vez antes do processamento, sem custo adicional por iteração.

Outro desafio importante foi evitar dupla contagem de ocorrências quando múltiplas threads inspecionam regiões adjacentes. A solução adotada nas implementações autorais foi o conceito de intervalo de propriedade, no qual cada thread é responsável apenas pelas ocorrências cujo índice inicial pertence ao intervalo que lhe foi atribuído.

Também houve dificuldades relacionadas à automação dos testes, incluindo:

\begin{itemize}[leftmargin=*]
    \item padronização da saída entre C e Java;
    \item correção de diferenças de locale na impressão de números em Java;
    \item integração com scripts Python para repetição de experimentos;
    \item interpretação correta dos dados exportados para CSV.
\end{itemize}

No caso da paralelização em Java, foi necessário ainda lidar com o custo de gerenciamento de threads e com a estrutura de \texttt{ExecutorService}. Já no caso do OpenMP, foi necessário ajustar a estratégia de divisão do trabalho e observar o impacto do número de threads sobre o desempenho final.

\section{Conclusão}

Este trabalho apresentou a implementação e análise de soluções sequenciais e paralelas para o problema de busca de substrings em arquivos de grande porte, utilizando o algoritmo Boyer-Moore-Horspool como base comum.

Os resultados demonstraram que a implementação em C apresentou melhor desempenho geral, tanto na versão sequencial quanto na paralela. Isso se deve principalmente ao menor overhead da linguagem e ao maior controle sobre memória e operações de baixo nível.

Entre as contribuições técnicas comuns às implementações em C e Java, destacam-se o cálculo do salto pós-match via \textit{KMP failure function}, que permite avanços maiores após cada ocorrência confirmada sem perder matches sobrepostos. Na versão em C, soma-se ainda o uso de \textit{double buffering} na versão paralela, que sobrepõe a leitura do próximo chunk ao processamento do atual, reduzindo o tempo ocioso das threads de CPU durante operações de leitura de dados.

A paralelização mostrou-se eficaz, especialmente para arquivos de tamanho intermediário, onde foram observados speedups superiores a 2x. No entanto, para arquivos muito grandes, o ganho de desempenho foi limitado por fatores de hardware, como largura de banda de memória e custo de acesso a disco.

A comparação entre Java e C evidenciou que, embora o Java ofereça maior abstração e portabilidade, o C ainda é mais eficiente para aplicações de processamento intensivo de dados.

Conclui-se que a melhor solução para o problema estudado foi a implementação paralela em C com OpenMP, por apresentar melhor desempenho e maior escalabilidade.

Como trabalhos futuros, destacam-se:

\begin{itemize}
    \item uso de técnicas SIMD e vetorização;
    \item comparação com outros algoritmos de busca;
    \item otimizações de cache e afinidade de threads;
    \item avaliação em diferentes arquiteturas de hardware.
\end{itemize}
